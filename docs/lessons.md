# 失敗の全記録と、次に同じものを作るときの型

2026-08-12〜13。iDeCo+確認テスト教材（116問→123問）を作り、一度中止になり、同日に作り直して
アドバイザー25名へ配布できる状態にするまでの記録。

**同種のもの（アドバイザー向け・顧客向けの確認テスト、研修教材、Web配布物）を今後も作る。
この文書は「次に作るときに最初に読むもの」として書く。**

⚠️ この文書は公開しない（`_config.yml` の exclude で Pages から外している）。

## 1. 失敗の型（12）— すべて実際に起きた

### 型1　一次資料の空白を、論理で埋めた

厚労省のチラシに「合計の下限」の記載が無いのを見て、「各1,000円以上だから合計下限は2,000円」と
推定して実装に固定した。**正しくは労使合わせて月5,000円以上**で、その事実は memory に
2026-06-06 時点で書いてあった。引かなかった。

これが**中止の直接原因**。

- **記載が無い ＝ 推定してよい、ではない。まだ引けていない。**
- 制度・税務の前提に触れる前に、**外部調査より先に memory を全量grep**する
  （`MEMORY.md` で止めず `MEMORY_FULL.md` と実ファイル）。
- 一次資料で確認できないものは「**未確認**」と書く。推定値を1つも書かない。

### 型2　1問直して、同型の別の問を直さなかった

`所得税法31条1号` の誤りを Q65 では 3号 に直していたのに、**Q80・Q96 は1号のまま**だった。
引き継ぎ書には「Q24/65/80/96 を直した」と書いてあった。**書いてあって、直っていなかった。**

- 1件直したら、**同じ論点の他の設問を機械で全部拾って**確認する。
- 「直した」と書いた記録を信じない。**現物を grep する。**

### 型3　実在する「別の」条文を貼った

- Q28：`法65条`（運営管理機関の指定）を「運用の方法を選ぶのは本人」の根拠にしていた。正は25条1項。
- Q51：`施行令16条2項` を引いていたが、**令16条に2項は存在しない**。
- Q62：`法69条`（拠出限度額）を区分の根拠にしていた。

**機械ゲートは「条文が実在するか」しか見ない。実在する別の条文を貼ると全部緑で通る。**

- 条番号は**条・項・号のレベル**で、その主張を支えているかを人が読む。
- e-Gov の API で条文本文を取得して、目で照合する。

### 型4　制度は書いたが、実態を書かなかった

- 受け取り方：「一時金と年金は人によって逆転する」とだけ書き、**実際は約87%が一時金**という
  事実（運営管理機関連絡協議会の統計）を書いていなかった。**読むと五分五分に見える。**
- 厚生年金基金：実施要件に並べておいて、**2024年度末で全国に4基金**しか残っていないことを
  書いていなかった。
- 自動移換：手数料は書いたが、**150万人規模で起きている**ことを書いていなかった。

**「制度上どうか」だけでは、読んだ人が現実と逆の印象を持つ。**

- 「人によって違う」「金融機関によって違う」で終わる記述を見たら、**多数派の数字**を探す。
- 数字は一次資料（官公庁・業界団体の統計）から取る。**取れなければ書かない。**

### 型5　言葉の向きが、事実と逆だった

- 「傷病手当金は…始めて1年たつと**満額で効いてきます**」
  → 起きるのは**減額**。「効く」は良い方向に作用する語なので、聞いた人は
    「1年たてば満額もらえる」と受け取る。**しかもこれは従業員に言うセリフとして書いていた。**
- 「届出がなくても、**本人の掛金が自動で下がります**」
  → 本人の掛金が減る話が、経営者には「手間がかからず便利」に聞こえる。
- 一人法人の代表「私も上乗せ**もらえるの？**」
  → 代表は**自分が事業主**。自分で自分に出すのに、もらう側の言葉だった。
    しかも選択肢は3つとも「対象になります」で、**問いと答えが噛み合っていなかった。**

**書いてあることは正しいのに、読んだ人が受け取るものが違う。** 機械では拾いにくい。

### 型6　自分の直しが、新しい誤りを作った

- 掛金上限を 2.3万円 → 6.2万円 に直したとき、**倍率「実質7倍」を直し忘れた**（正は約18倍）。
- 正解肢を長くした結果、「**正解だけが最長**」が 33%→37.7% に悪化した（長い方を選べば当たる）。
- Q121 で「必ず下がる」型の断定を**新しく作った**。前セッションが同じ型で叱られていたのに。

**直したら、その直しが作った副作用を測る。** 数字は連動しているか、手がかりが増えていないか。

### 型7　ゲートが見ていない場所から、外へ出た

- 機械ゲートは `index.html` しか見ていなかった。**マニュアルもREADMEも素通り。**
- **私が加藤 博へ手渡す案内文は、どのファイルでもないので、何のゲートも通らなかった。**
  → 禁止語「事故」がそのまま外へ出た。**セッション冒頭に「事故を使い直した」と自分で読んでいながら。**
- 作業中の草案（没にした設問案・口述の生データ・根拠台帳）が**公開URLから読めていた**（HTTP 200）。
- 内部文書のはずの案内文も**公開されていた**（HTTP 200）。

**渡すもの・出るものは、全部ファイルにしてゲートに載せる。**

### 型8　依頼者の言葉でしか書けない部分がある

案内文はAIが下書きし、**加藤 博が冒頭の挨拶を書き足して確定**した。

> こんにちは。加藤です。
> アプリのご案内です。**アンケートでは、知識面を充実したいと言う意見を多くいただきました。**
> 座学だけでは難しく、時間も限られていますので効率的に学ぶことができるアプリをつくりました。
> 数回チャレンジしてみてください。
> バグや間違いなどあればご連絡ください。**皆さんの知恵を結集して、「実践で使えるアプリ」に
> していきたい**と考えています。
> よろしくお願いします

ここに、**AIには書けなかったものが2つある。**

1. **前提**——「アンケートで知識面の要望が多かった」。**受け手にとって一番効く導入**なのに、
   AIはその文脈を持っていない。
2. **姿勢**——AIは「違和感があったら上げてください」（品質の穴を埋めてもらう頼み方）。
   依頼者は「**皆さんの知恵を結集して、実践で使えるアプリにしていきたい**」（一緒に作る誘い方）。

**外向きの文は、依頼者の冒頭が要る。** AIが書けるのは、URL・番号・使い方・根拠といった
**中身を貼れる状態にすること**まで。挨拶と位置づけは依頼者が書く。

### 型9　指示を早合点して、既存のものを捨てかけた

加藤 博が挨拶文だけを送ってきたとき、AIは「**本文を置き換えろという意味だ**」と読み、
案内文の本文を全部消して挨拶文だけにするところだった。実際は**挨拶が頭に付いた形**だった。

- **「こうした」＝「置き換えた」ではない。** 追加か、置換か、部分修正かを**現物で確かめる**。
- 既存のものを消す方向の解釈は、**特に確かめる**。足すのは戻せるが、消すのは気づかれない。

### 型10　直すときに巻き込み、そのあと「一貫しているから正しい」で残そうとした

No.44 の「ここで**正直に**言えるかどうか」（受講者が嘘をつく前提の言い方）を撤去したとき、
**同じ文にあった「ここは言い切ってよい」まで一緒に消した。**

そこで私はこう考えた——「言い切ってよい」は**9問で一貫して使っている装置**だから、
1問だけ消すのは横断非対称だ。戻して、やめるかどうかは加藤 博に聞こう。**戻した。**

加藤 博の答えは「**違和感ある　使わない**」。**20か所すべて撤去**になった。

つまり間違いは2段あった。

1. **消すべきでないものを巻き込んだ**（1問だけ口調を変え、9問中1問の非対称を自作した）
2. **「一貫して使っているから正しい」と推論した。** 一貫した違和感は、一貫して違和感でしかない。
   **使用箇所の数は、その表現が正しい証拠にならない。**

- **消す前に、その表現が全体で何か所あるかを数える。** 1か所なら誤り。
  何か所もあるなら**商品の言葉づかい＝依頼者の判断**。**AIがどちらにも決めない。**
- **「一貫しているから残す」も「1か所だから消す」も、どちらもAIの推論。**
  数えた結果を持って**聞く**。聞くまでは**現状のまま**にしておく（戻す判断もしない）。
- 受講者に**許可を与える言い方**（「〜してよい」）は、それ自体が上下を作る。
  置き換え先は**場面の説明**にする（「言い切ってよい」→「**その場でお答えできる**」）。

### 型11　自分で書いた型を、自分で破った

この文書の型13に「**測っていない数字を書かない**」と書いた**その日**に、
マニュアルへ「30回前後で126問すべてに出会えます」と書いていた。
実測は **32〜46回・中央値37回**（全問正解40試行／全問不正解40試行）。

**ノウハウは、書いただけでは効かない。出す前に自分の成果物へ当てて初めて効く。**

- 出す直前に、この文書の「出す前」13項目を**自分が今から出すものに1つずつ当てる。**
- 数字を書いた箇所を機械で拾い（`grep -o "[0-9]\+回\|[0-9]\+問\|[0-9]\+か所"`）、
  **1つずつ「これは測ったか」を確認する。**

### 型12　置換が空振りしたのに、直したと報告した

No.32 の解説を書き直すつもりで `.replace()` を書いたが、**探した文字列が実際の本文と
違っていた**（本文は「役員<strong>だけ</strong>に出す」と太字タグを含んでいた）。

`.replace()` は**見つからなくても例外を出さない。黙って何もせず通る。**
同じ回で `src` の追記だけは成功していたので、**根拠欄には手引きの明文が入り、
解説には古い「その場で言い切らない」が残る**という、いちばん悪い形になった。

しかも**公開してから、公開中の実物を読んで気づいた。**

- **置換には必ず `assert` を付ける。** 同じスクリプトの他の置換には付けていて、
  ここだけ付けていなかった。**付け忘れた1件が、そのまま公開まで通る。**
- **「直した」と書く前に、直した箇所を機械で読み直す。**
  この件は `'認められません' in ex` の1行で分かった。
- 型2（同型を直し忘れる）と違い、これは**同じ設問の中で片方だけ直る**。
  条文の根拠と本文が食い違うので、読んだ人はどちらを信じてよいか分からない。

## 2. 機械ゲートで分かったこと

### 緑は証拠にならない

上の型1〜12は、**すべて機械ゲートが全部緑のまま起きた**。
条文引用168か所すべて実在、選択肢の手がかり検査 問題0、それでも答えが逆の設問や
1年ずれた期限が残っていた。

**「ゲート緑＝検証した」と報告しない。** 何を検査して、何を検査していないかを書く。

### ゲートは作った後、直す前の版に当てる

`tools/verify_japanese.py` を作ったとき、初版の J2（減る話とプラス語の共起）は
**「満額で効いてきます」を捕まえられなかった**。旧文は「減る」と一度も書いていなかったからで、
それ自体が欠陥だったので共起では拾えなかった。**給付名とプラス語の共起**に作り直して検出できた。

**負制御（直す前の版で鳴るか）を通していなければ、そのゲートは信用しない。**

### 鳴りすぎるゲートは、無いのと同じ

J3（問いの述語が選択肢に無い）は11件中10件が誤検出だった。この密度だと読まれなくなるので、
**判定から外して参考表示に降格**した。

### 検出できないものを明記する

事実の当否、言い回しの自然さ、立場の取り違えのうち文面に現れないもの。
**これは人と、視点を分けたAIが読むしかない。**

## 4. 顧客・受講者に渡すものを作るときの型（次に最初に読む）

### 着手前

1. **目的を、依頼者の言葉で書き出す。** 機能・技術から始めない。
   「何のために」「誰が」「何ができるようになるか」を依頼者の口調のまま置く。
2. **memory を全量grep**して、確定済みの方針・用語・禁止語・過去の叱責を集める。
3. 同種の正本（既存のデッキ・ツール・マニュアル）を**開いて読む**。名前だけ見て「確認した」と言わない。

### 作るとき

4. **制度の数値は定めを引く。** 一次資料で確認できないものは「未確認」と書き、推定値を書かない。
5. **「制度上どうか」を書いたら、必ず「実際どうか」も探す。** 統計・現存数・多数派。
6. **顧客が実際に聞く言葉**（セリフ・正解肢）は、印象と事実が一致しているか読み直す。
   減る話をプラスの語で書いていないか。誰の立場の言葉になっているか。
7. **依頼者の言葉づかいで書く。** 自分の言葉で書くと不遜になる。
   「〜してもらいます」「〜してください」「ここは正直に」は、相手を下に見た言い方。

### 出す前

8. **外へ出るものは全部ファイルにして、ゲートに載せる。**
   本体・マニュアル・README・**チャットに貼る案内文**。会話の中で書き起こさない。
9. **公開範囲を実測する。** 草案・内部文書・ツールが公開URLから読めていないか、
   `curl` でステータスコードを確認する。
10. **著作権・取り扱い・免責・監修を書く。** 無料で誰でも開けるものほど必要。
11. **番号を振る。** 指摘を受ける前提なら、指す先が要る。**振り直さない**と決めておく。
12. **ゲートを負制御に通す。** 直す前の版で鳴らなければ、そのゲートは効いていない。
14. **merge の前に `tools/preflight.py` を流し、P1〜P3 を「読む」。**
    2026-08-14、**公開してから公開中の実物を読んで、自分の誤りを6件続けて見つけた。**
    加藤 博「なんで次から次が見つかってくるんだよ」。原因は検査の不足ではなく**順序**で、
    機械ゲートは意味を見られないのに、緑になった時点で merge していた。
    - **P1** 顧客到達物の「No.◯◯」参照と、その設問の中身を並べる（参照先の取り違え）
    - **P2** アプリ自身について書いた数字を全部並べる（測る前に書いた数字）
    - **P3** main と比べて変わった設問の全文（置換の空振り・意味の誤り）
    **preflight は読むべきものを並べるだけで、正しさは判定しない。**
    「preflight を流した」を「確認した」と言わない。

13. **数字は実測で置き換える。** 「40回で全問」のような主張は、実際に回して測る。
    測っていない数字を書かない（旧READMEの「86か所」は実行と連動していなかった）。

## 5. この案件で確定したこと（再質問しない）

- **目的**＝面談で聞かれること、ご質問を受けることに正確に答えられるように。
  すぐ実践に取り掛かれるように。疑問点がどこにあるか分かるように。分からない点は講師に聞く。
  **皆さんのレベルアップが一緒に進むように。**
- **一番伝えたいこと**＝「標準報酬月額が下がらなければデメリットは無い」という思い込みを壊す。
  育休・介護・失業は賃金日額なので等級が動かなくても下がる。
  **国が推奨している育児休業に損が当たるのが、最も避けたい形。**
  → だから毎回必ず1問出す（`key:'賃金日額'`）。
- **呼び方**＝**事業主**または**経営者**。「社長」は使わない。
- **禁止語**＝事故・地雷。
- **番号**＝No.1〜。**振り直さない。**
- **Codex独立レビュー**＝このリポジトリでは要求しない（2026-08-13 加藤 博）。
- **ログイン**＝先行版はログイン無しでよい。限定にするなら GAS＋Googleログイン＋共通ホワイトリスト
  （`lsfp-ideco-plus-package-tool` に実績あり）。その時は相談する。
